# 淘宝活动监控项目 · 踩坑复盘

> 目的：把项目从 2026-09 开发至今踩过的所有坑沉淀下来，任何会话接手时先读本文，直接避开已知问题，提高效率。
> 维护规则：每次踩了新坑、修了新 bug，把「现象/根因/解法/预防」追加进对应分类。

---

## 0. 项目铁律（用户强规则，最高优先级）

| # | 规则 | 说明 |
|---|---|---|
| 1 | **需求不清必须先提问** | 对需求有疑问/不确定时，先向用户提问直到搞懂，不得擅自假设再动手 |
| 2 | **首要保证活动检测稳定性** | 优先级排序：检测稳定性 > 代码流畅性/安全性 > 每轮耗时 |
| 3 | **安装/下载用 npmmirror** | 国内镜像优先，避免 GitHub 等国外源下载慢 |
| 4 | **单文件拆分保 HTML 全量** | 拆分时保留 script 块之后到 `</body>` 的全部元素，用全量核对脚本（id/事件/文本/样式/脚本逐项比对）验证 |
| 5 | **删除文件永久删除** | 不进回收站，直接抹掉 |
| 6 | **避免重复检测触发风控** | 任何改动不得导致同一店铺短时间内被反复登录/扫描 |

## 1. 登录与风控（最容易翻车的区域）

| 坑 | 现象 | 根因 | 解法 / 预防 |
|---|---|---|---|
| 登录态复用失败 | 用已保存登录态打开页面直接跳 `loginmyseller.taobao.com` | 淘宝登录态（profile cookie）频繁失效 | **一律密码登录**，不要浪费时间做登录态复用 |
| 密码登录失败即整轮失败 | 一家店密码错误/需额外验证 → 该店本轮直接失败 | 旧逻辑：失败立即 throw | 失败时**自动弹可见窗口等人工过验证**；失败店铺挂起、其他店铺照常检测（人工干预次数减半） |
| 触发短信/滑块风控 | 连续多轮检测后要求短信验证 | 同一账号短时间内多次登录/扫描 | **不要多次重复检测**；手动/定时排期错开；重启带 `--delay` 对齐排期，禁止重启后立即全量 |
| 登录域名漂移 | 蔻丝旗舰店登录网址变成淘宝（非千牛） | 淘宝端路由变化 | 遇到"直接登录失败：提交后仍停留在登录页"，先确认当前登录 URL 与预期是否一致 |
| profile 副本实验无效 | 复制 profile 到临时目录打开，仍跳登录页 | 登录态本身失效，与目录无关 | 验证页面行为前先确认登录态；失败就转密码登录 |
| 单店检测参数错误 | `node monitor.js --shop=LPZY` 走了全量 9 店检测 | **单店铺检测必须带 `--once`**：`--once --shop=<KEY>`；只带 `--shop` 会进 daemon 全量分支 | 启动任何手动检测前，命令里必须同时带 `--once --shop=`；跑前先确认进程命令行 |

## 2. 页面扫描（异常 tab）—— 误报/漏报高发区

| 坑 | 现象 | 根因 | 解法 / 预防 |
|---|---|---|---|
| 点击异常 tab 列表未切换 | 抓到的是"全部商品"第一页 10 个，标注却说 1-9 个 → 批量误报 | Fusion tabs 点击后 aria-selected 立即变 true，但列表异步加载慢；点击前需等待列表真正切换 | 无条件进入"切换等待"：记录点击前首行，轮询到首行变化（最多 10 秒）才抓取 |
| 首行恰好相同 → 误判未切换 | 良品主义：点击异常 tab 后列表实际切换成功，但新/旧列表首行是同一商品 ID（1036126114842），10 秒观察不到变化 → 连续多轮"扫描无效" | 切换判定只比较首行 | **用前 5 行 ID 签名对比**代替首行：首行巧合时通过 2-5 行识别切换；真未切换时签名必变，防误报不降（提交 4e97e89） |
| 页面渲染异常（外壳在、列表空） | 截图里页面壳/双11横幅/tab 都在，商品行区域空白；日志却显示"点击前首行有值" | 淘宝页面端渲染不稳定（大促期尤其明显，双11现货页多次出现） | 三次重试兜底：重试时刷新页面，页面恢复正常即成功；确认是页面端问题而非代码问题后再人工打开页面核验 |
| 数量合理性校验拦截批量误报 | 抓到数 > 监控数 3 倍且 > 30 → 判定扫描无效、不比对不报警，瞬时重试 | 渲染异常把全部商品列表当异常名单 | 保留该防线；重试仍失败才通知人工查看 |
| 异常 tab 无数字（无标注） | 「异常」不带 (N) = 当前无异常商品，空列表正常；但若抓到全部商品（如 171 个）说明列表未切换 | 无标注 + 抓到全量 = 点击未生效 | 快速止损：无标注且抓到 >30 个立即判扫描无效，终止翻页（省 2 分钟+） |
| 翻页失败（停留第 1 页） | 抓到 10 个 > 标注 9 个，被判扫描无效 | 列表切换成功但异常名单只有一页（无下一页）；旧逻辑把"超过标注"一律当未切换 | **区分已确认切换与未切换**：签名已变化（列表确已切换）时，异常数略超标注只警告、保留已抓 ID 继续比对；签名未变才判扫描无效 |
| tab 标注滞后 | 页面标注 9 个、实际抓到 10 个 | 后台计数异步刷新 | 已确认切换时容忍轻微超量（10 vs 9），以抓到 ID 为准 |
| 错误截图是唯一现场 | 报"扫描无效"后截图列表区为空 | 截图时机在多次刷新后 | 截图+日志双记录；复盘时先看截图再下结论，截图与日志矛盾时以更接近现场的证据为准 |

## 3. 调度与并发（单实例）

| 坑 | 现象 | 根因 | 解法 / 预防 |
|---|---|---|---|
| 手动检测忘带 `--once` | 直接触发 9 店全量（上一条已提，最易犯） | `--shop` 单独不触发单店分支 | 启动手动检测后**立即确认进程命令行**含 `--once` |
| 定时/手动并发抢 Chrome | 两个进程共用 profile/端口，互相覆盖结果文件 | 无互斥 | `data/detect-lock.json` 互斥锁：手动启动时定时在跑 → 拒绝启动（定时优先）；锁持有者进程死 → 自动接管 |
| 手动结束后的排期 | 手动检测完很快又触发定时轮 → 风控 | 排期仍按原计划 | 手动结束后**一律按「手动结束时间 + interval」重排**（无论早于/晚于原计划），避免连续检测 |
| 停止当前检测 vs 关闭定时检测混淆 | 用户以为"停止自动检测"能停当前轮 | 两个按钮语义不同 | 「停止当前检测」= 写 stop-cycle.flag，运行中轮次下个检查点中断；「关闭定时检测」= 写 monitor-paused.flag，停掉整个自动巡检（需点「开启定时检测」恢复）。后者严重级高，按钮做红色实心 + 确认弹窗 |
| 中断轮污染结果文件 | 轮次中断后结果文件只剩已跑店铺，未跑店铺消失 | 中途写结果 | 中断轮不覆盖结果文件，保留上一轮完整数据（已修） |
| 重启不带 delay | 重启后立即全量检测 9 店 → 风控 | 守护/手动重启默认立即跑 | 一切重启带 `--delay=N` 对齐下一排期（如 13:42 重启、下一轮 14:16 → `--delay=34`） |
| 手动检测被取消后 daemon 死等 | daemon 等不到 manual-done 挂起 | 无超时 | 等待手动结束加 30 分钟超时兜底；`--once` 进程收到 SIGTERM/SIGINT 先写 manual-done + 释放锁再退出 |
| 手动结束自动恢复定时 | 手动检测前若暂停了定时，结束后应自动恢复 | 遗漏 | `--once` 结束时若检测前暂停了定时会自动恢复 |

## 4. 进程 / 守护 / 运维

| 坑 | 现象 | 根因 | 解法 / 预防 |
|---|---|---|---|
| 守护与心跳的认知混淆 | 一度设计"心跳文件（90s TTL）"判定存活，改完未 git 提交，后被回滚覆盖 → 代码里没有心跳，`data/monitor-heartbeat.json` 成了 10-14 的陈旧残留 | **改造完成必须立即 git 提交**，否则随时可能被后续操作覆盖丢失 | 当前守护 = 计划任务「淘宝活动监控-守护」每 5 分钟跑 VBS，**查 node 进程命令行**（`monitor.js`）是否存活，存活则不拉起；心跳残留文件无害、可删 |
| 守护拉起不带 delay | monitor 意外退出被守护拉起 → 立即全量检测（风控风险） | VBS 里 `node monitor.js` 无 `--delay` | 已知限制：守护拉起是"尽快恢复"优先，牺牲 delay；若需避免，可在 VBS 里加按排期计算 delay 的逻辑（未做，慎改） |
| 启动器"Failed to fetch 启动失败" | 冷启动时启动器调 `/api/monitor/status` 超时 | 接口每次冷启动 PowerShell 查 CIM 进程，2.6→4.6 秒递增，超过启动器超时 | 超时放宽到 6000ms + 失败文案改"无法连接"（10-12 改动，需确认当前版本仍在） |
| 凌晨内存膨胀 | 长期运行内存缓慢上涨 | Node/浏览器实例累积 | 每日 04:00「淘宝活动监控-重启」计划任务自动重启释放内存；重启带 delay 对齐当天排期 |
| 服务卡住（一轮跑 25 分钟） | 单轮远超正常 5-6 分钟 | 店铺反复登录/扫描重试叠加（如某店页面异常） | 先确认是否在正常重试窗口内；卡住就停进程重启 + 清理残留锁 |
| 日志两份容易看混 | monitor.log 与 admin-server.log 分开，还有根目录 monitor.log 句柄占用 | 历史遗留 | 已统一日志路径；`logs/error-<店KEY>-<ts>.png` 为错误截图，按店+时间定位 |
| 局域网端口被关 | 外部访问失败 | 公司网络/防火墙变化 | 端口 3080；需要外网时曾用 cpolar（后因公司零信任停用，改纯内网 + 口令/花名门禁） |

## 7. 开发习惯（直接提高效率）

| 坑 / 教训 | 说明 |
|---|---|
| **改完立即提交** | 10-12 心跳改造未提交被回滚覆盖 → 白白损失一版功能。任何改动：改完 → 语法检查 → 测试 → 立即 `git commit` |
| **`--once` 必带** | 手动单店检测忘带 `--once` 会变全量（9 店登录 = 风控风险 + 时间浪费），启动后确认进程命令行 |
| **避免变量遮蔽** | 外层已声明 `listChanged`，块内又声明同名变量 → 外层永远读不到（实际 bug 出现过一次） |
| **npmmirror** | 安装依赖/下载一律 `--registry=https://registry.npmmirror.com` |
| **PowerShell 查 JSON 用 node** | 见"数据与文件"节 |
| **重启必须对齐排期** | 所有重启操作带 `--delay`，从日志找"下次检测将在 X 分钟后执行"计算对齐 |
| **截图+日志双现场** | 页面类 bug 一定有错误截图；复盘先看图再读日志 |
| **大促期页面不稳定是常态** | 双11现货页等大促页面渲染异常概率高，代码要做重试兜底，不要一失败就改代码 |
| **git commit 不用 --no-verify** | 除非用户明确要求，不要跳过 hooks |

## 9. 报警放大类隐患（2026-10-28 审查，2026-10-29 已修 2 条）

> 背景：用户反馈「最近店铺异常频率偏高」，对照 logs/monitor.log、data/state.json、logs/error-*.png 复查后确认，除大促页面本身不稳定外，代码有 3 处会把偶发抖动放大成重复报警/整店判异常。
> **2026-10-29 处理结果**：前两条已修复，并由 `tests/cooldown-loop.js`、`tests/scan-loop.js` 两个回归脚本锁死（改完跑一遍，绿=没退化）；第三条暂不修（当前商品级报警已归零，优先级低）。修之前这两条各有一次真实「红」记录，别再从头查一遍。

| 坑 | 现象 | 根因 | 状态 |
|---|---|---|---|
| 店铺故障提醒冷却失效 | 同一店铺、同一种故障，在 `errorAlertCooldownMinutes`（180 分钟）内仍被重复推送；大促页面抖动期钉钉明显变吵 | `maybeSendErrors` 用「店铺:完整错误文本」拼 key，而文本里带商品 ID 与抓取数量，每轮都变 → key 永不相等；另外「只要一轮没店铺故障就清空 key」，抖动店等于每轮都能推 | **已修（2026-10-29）**：冷却改为按「店铺 + `classifyShopError().title`」记时（`state.shopErrorAlertAt`），不再因无故障轮清空；同时在推送成功/抑制时各写一条日志，解决「推了几次查不到」的可观测缺口。回归：`node tests/cooldown-loop.js`（修前 A1/A3 红 → 修后全绿） |
| 异常名单「数量不符」整轮丢弃 | 日志出现「数量不符：抓到 11 个，页面标注 1 个」，该店整轮判店铺异常、当轮完全不做异常比对 | `scanAnomalyTabWithRetry` 的 `merged` 是跨 3 次重扫累加的 Set，判定却用 `merged.size === declaredCount`：第 1 次抓到超量后，第 2 次即使抓到干净的 1 个也会因累加值不等于标注而被判失败 | **已修（2026-10-29）**：改为每轮独立 Set、哪轮成功采用哪轮；另把「页面未标注数量却抓到商品行」分支改为先看 `listChanged`（列表签名），已确认切换时只警告并采用，不再一律判扫描无效。回归：`node tests/scan-loop.js`（修前 B1 红 → 修后全绿） |
| 店铺失败一轮 → 商品报警去重被清空 | 某店检测失败后的下一轮，该店原有的商品级异常会重新按“首次异常”推一次钉钉（重复报警） | `diffProductAlerts` 在全量轮从零重建 nextAlerts，失败店铺没有任何结果，它旧的 `productAlerts` 就丢了；中断轮有 `preserveUnseen` 保护，但“店铺失败”这条路径没有 | 未修（2026-10-29 复查：商品级报警推送 10-21 起已归零，暂无实际影响）。要修：把本轮失败的店铺集合传进去，失败店铺的旧报警状态原样继承、不参与比较 |

补充两条**已排除**项，避免下次重复怀疑：

- **每轮都完整走一次账号密码登录不是 bug**：无头（builtin）模式下登录态就是保存不住，必须每轮重登，属设计取舍（2026-10-28 用户确认）。
- **cdp 模式掉线自动开登录窗口弹不出来**：`promptManualLogin()` 在监控自己的 persistent context 还没关闭时调用 `shop-login.js`，同一 profile 目录会被 Chrome 单实例锁挡住，且子进程 `stdio:'ignore'` 看不到失败。内置模式（当前部署）本来就无可见窗口，实际影响小；若将来切 cdp 模式再修。

### 还没闭环的两条（要真机/真页面才能验）

- **`withTimeout` 只是 `Promise.race`，不取消底层任务**：`shopTimeoutMinutes`（30 分钟）超时后，那轮仍在后台登录/占浏览器，下一轮叠加，`state.json` 里 KS 的「店铺检测超过 30 分钟未返回」即此。要修：接 `AbortSignal`，超时主动关 context。风险：改错会把正常轮一起砍掉，需真机验证。
- **`firstRowsSignature` 的 `beforeSig === ''` 被当成“已切换”**：首屏行渲染晚到时会被误判为列表切换，进而调用 `tab.count == null` 的新分支拿到全部商品列表。要验必须先有真页面，目前只用日志佐证。

## 附：一键排查清单（遇到问题按此走）

1. **看日志**：`Get-Content logs\monitor.log -Tail 60 -Encoding UTF8`（最近一轮做了什么）
2. **看截图**：`logs\error-<店KEY>-<ts>.png`（页面现场）
3. **看进程**：`Get-CimInstance Win32_Process -Filter "Name='node.exe'" | ? { $_.CommandLine -match 'monitor|admin' }`（有无重复/遗漏）
4. **看锁**：`data\detect-lock.json`（是否有检测在跑；pid 是否存活）
5. **看排期**：日志里"下次检测将在 X 分钟后执行"
6. **确认暂停状态**：`data\monitor-paused.flag` 是否存在（存在 = 定时检测被关闭）
7. **查 git**：`git log --oneline -5`（最近改了什么，是否提交）
8. **验证 JSON**：一律用 node，不用 PowerShell `ConvertFrom-Json`
9. **觉得“店铺异常频率变高”**：先看本文第 9 节（3 条“报警放大”隐患，已修 2 条、1 条待定），别当成新问题从头查；再按 1~7 条确认是不是大促页面抖动或风控
10. **改过报警/扫描逻辑后**：`node tests/cooldown-loop.js` 和 `node tests/scan-loop.js` 各跑一遍，两条都要 PASS（退出码 0）才算没退化
